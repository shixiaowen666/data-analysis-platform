# 问答质量管理 · 自动调优设计文档

> 版本：v1.0　|　状态：已评审确认　|　前置：`01-问答质量管理方案.md`　|　原型：`docs/prototype/`（页面 ⑧–⑩）
>
> 范围：**定位出问题后 → 手动触发调优 → 自动验证 → 查看验证结果 → 发布 / 回退** 的完整闭环。

---

## 1. 目标与边界

### 1.1 目标

管理员在诊断页完成错误定位后，不再需要"跳到各个管理页手改 → 自己去问数页重试 → 凭感觉判断好没好"，而是：

1. 系统根据**错误类型 + 定位结论**自动给出**调优建议**（改什么、改成什么）
2. 管理员确认/编辑后**一键触发**，变更先落到**草稿（Draft）**，不影响线上
3. 系统自动用**验证集**（原问题 + 同类历史问题 + 回归集）跑一遍，给出**前后对比**
4. 管理员看结果：通过 → **发布**；不通过 / 有副作用 → **回退**（一键恢复到调优前快照）
5. 全过程留痕，可审计、可追溯

### 1.2 不做什么（本期）

- 不做无人值守的全自动调优：**每一次变更和发布都需要人确认**，系统只负责"建议 + 执行 + 验证 + 回退"
- 不做提示词的 **LLM 自动改写**（Phase 3 可选项，见 §9）；但**提供提示词编辑器**（基于当前版本新建、diff 对比、语法检查），由管理员手工修改
- 不做底层数据修复（`fix_type = DATA` 的问题走数据治理流程）
- 不做模型微调

### 1.3 核心原则

| 原则 | 含义 |
|---|---|
| **草稿隔离** | 调优变更先写入草稿态，验证通过后才发布到线上；验证期间线上问数不受影响 |
| **快照可回退** | 发布前自动对所有被改动的资产做快照；回退 = 恢复快照 + 触发下游同步 |
| **验证先于发布** | 没有验证结果不允许发布；验证"退化"（原来对的变错了）必须显式确认才能发布 |
| **一事一单** | 一个调优任务（TuningTask）对应一个诊断结论；一个任务可包含多条变更（如同时改表描述 + 加别名） |
| **影响范围可见** | 发布前展示"这条资产变更会影响哪些智能体 / 哪些历史问题" |
| **发布需审批** | 任何任务发布到线上必须经**超级管理员**审批通过；回退不需审批（止损优先），但事后通知超级管理员 |

## 2. 可调优资产清单（What can be tuned）

调优的本质是修改下面这些"决定模型怎么选、怎么算、怎么说"的资产。按错误类型映射：

| 资产 | 所在模块 / 存储 | 影响链路环节 | 对应错误类型 | 现状是否有版本 | 变更生效方式 |
|---|---|---|---|---|---|
| **表描述**（`tb_description` / `note`） | bi-manager `olap_table_pro` | ①召回 ②拆解选表 | 选表错误 | ✗ 直接覆盖 | 改库 → 触发 recall `meta_sync` → 下次提问生效 |
| **指标/维度 别名、中文名、口径描述** | bi-manager `olap_basic_pro.alias / chinese_name`、`olap_basic_pro_indicator.caliber_description` | ①召回 ③取数映射 | 指标/维度提取错误 | ✗ | 同上 |
| **列级聚合类型 `agg_type`**（`summary`） | bi-manager `olap_table_field_mapping.summary` | ②拆解（快照/累计/率规则） ④执行 | 拆分错误（口径类） | ✗ | 改库 → 下次提问生效（chat-server 实时组装） |
| **维度枚举值 `possible_values`** | bi-manager `olap_basic_pro_dimension.value_entries` | ②拆解 filter | 维度错误 | ✗ | 同上 + recall sync |
| **智能体知识库**（`business_context`） | chat-server `ai_body_knowledge_info` | ②拆解 ⑤总结 | 意图识别错误、口径类 | ✗ | 改库 → 下次提问生效 |
| **智能体绑定表** | bi-manager `dcar_ai_body_relation` | ①召回范围 | 选表错误 | ✗ | 同上 |
| **拆解提示词** | System B `prompt_group(main) / prompt_version` + 文件 | ②拆解 | 拆分错误、意图识别错误 | ✓ 已有版本 + switch | 新建版本 → switch 激活 |
| **总结提示词** | System B `prompt_group(summary)` | ⑤总结 | 总结错误 | ✓ | 同上 |
| **召回配置**（top_k / 阈值 / 路径开关） | recall-service `recall_config` | ①召回 | 选表错误、指标维度错误 | ✗（30s 热刷新） | 改库 → 30s 后生效 |
| **召回领域知识 / 同义词** | recall-service `domain_knowledge.json`、rewrite 词典 | ①召回 | 选表错误、指标维度错误 | ✗ 文件 | 改文件 → `/api/rewrite/reload` |

> **结论**：除提示词外，其它资产都没有版本机制。调优功能需要**统一的资产快照与变更记录层**（§4.2），而不是依赖各资产自身。

## 3. 调优闭环总体流程

```
 诊断页「保存定位结论」
        │
        ▼
 ┌──────────────────────┐
 │ ① 生成调优建议        │  规则引擎：错误类型 × 定位字段（应选表/应为指标…）→ 建议变更列表
 │   (TuningSuggestion) │  每条建议 = {资产类型, 目标对象, 字段, 当前值, 建议值, 理由}
 └──────────┬───────────┘
            ▼  管理员勾选 / 编辑建议值 / 手动追加变更
 ┌──────────────────────┐
 │ ② 创建调优任务        │  TuningTask(status=DRAFT) + N 条 TuningChange
 │   + 资产快照          │  对每个被改资产：记录 before 值（AssetSnapshot）
 └──────────┬───────────┘
            ▼  点「执行并验证」
 ┌──────────────────────┐
 │ ③ 应用到草稿态        │  各资产按 §5 的"草稿机制"写入，不影响线上
 │   status=APPLIED     │
 └──────────┬───────────┘
            ▼
 ┌──────────────────────┐
 │ ④ 自动验证            │  组装验证集 → 以 draft 模式调 System B /analyze
 │   status=VERIFYING   │  → 逐题对比 before/after → 产出 VerifyReport
 └──────────┬───────────┘
            ▼
 ┌──────────────────────┐
 │ ⑤ 查看验证结果        │  原问题是否修复 / 回归集通过率 / 退化清单 / 逐题 diff
 │   status=VERIFIED    │
 └────┬────────────┬────┘
      │通过         │不通过 / 有退化
      ▼            ▼
 ┌─────────────┐ ┌─────────┐
 │ ⑥ 提交审批   │ │ ⑦ 回退   │  恢复 AssetSnapshot → 触发同步 → status=ROLLED_BACK
 │PENDING_APPR.│ │(或改建议重跑)│
 └──────┬──────┘ └─────────┘
        ▼  超级管理员审批（通过 / 驳回）
 ┌─────────────┐
 │ ⑧ 发布       │  写库 → 下游同步 → 线上复验原题
 │ PUBLISHED   │
 └──────┬──────┘
        ▼
 发布后观察期：若线上再次出现同类负反馈 → 可从任务详情「回退已发布」
```

### 3.1 状态机

```
DRAFT ──执行──▶ APPLIED ──验证中──▶ VERIFYING ──完成──▶ VERIFIED ──发布──▶ PUBLISHED
  │                │                    │                  │                  │
  │取消             │失败                 │失败/超时          │回退               │回退（恢复快照）
  ▼                ▼                    ▼                  ▼                  ▼
CANCELLED       FAILED               FAILED           ROLLED_BACK        ROLLED_BACK
                                                          ▲
                                       VERIFIED ──修改建议重新执行──▶ APPLIED（新一轮，round+1）
```

| 状态 | 含义 | 允许操作 |
|---|---|---|
| DRAFT | 建议已生成，未执行 | 编辑变更、执行、取消 |
| APPLIED | 变更已写入草稿态 | 等待验证（自动） |
| VERIFYING | 验证集执行中 | 查看进度、中止 |
| VERIFIED | 验证完成，有报告 | 提交审批、回退、修改重跑 |
| PENDING_APPROVAL | 已提交超级管理员审批 | 审批通过 / 驳回（超级管理员）、撤回（提交人） |
| PUBLISHED | 已生效于线上 | 回退已发布 |
| ROLLED_BACK | 已恢复快照 | 查看、复制为新任务 |
| FAILED / CANCELLED | 终态 | 查看 |

## 5. 调优建议生成（规则引擎）

### 5.1 规则表（初始内置）

| # | 错误类型 | 触发条件（来自诊断结论 + trace） | 建议变更 | 建议值生成 |
|---|---|---|---|---|
| R1 | 选表错误 | `expected_table` 已填，且该表不在召回结果中 | `TABLE_DESC` 追加关键词 | 从原问题中抽取与应选表相关、但当前描述中不含的名词（如「分压」「电压等级」），追加到描述末尾："…；支持按分压/电压等级查询线损率" |
| R2 | 选表错误 | `expected_table` 已填，且该表**在**召回结果中但模型没选 | `TABLE_DESC` 增加区分性描述 + `KNOWLEDGE` 加一条区分规则 | 对比应选表与实际表的描述，生成区分语句："分区线损率按区局统计（view_..._fenqu），分压线损率按电压等级统计（view_..._by_voltage）" |
| R3 | 选表错误 | 应选表不在智能体绑定表内 | `AGENT_TABLE` 绑定该表 | — |
| R4 | 选表错误 | 召回 metaAfter 很小（≤2）且应选表未命中 | `RECALL_CONFIG` 调大 table 路径 top_k | 当前 top_k × 1.5，上限 20 |
| R5 | 指标错误 | `entity_fix[].expected` 已填 | `ENTITY_ALIAS` 为应选指标追加别名 | 别名 = 原问题中指向该指标的词（如「分压线损率」）；若实际指标与应选指标 code 相同但跨表，追加表限定描述 |
| R6 | 维度错误 | 同上 | `ENTITY_ALIAS` 维度追加别名；若 filter 值未命中 → `DIM_VALUES` 补充枚举值 | 例：user_type 枚举补「公线专变客户」 |
| R7 | 指标/维度提取错误 | step_trace 存在 `unmatched_columns` | `ENTITY_ALIAS` 把未映射列名作为别名加到最接近的实体 | 用 recall 的 embedding 找 top1 相似实体，置信度 < 0.8 则标"需人工确认" |
| R8 | 拆分错误（口径） | 根因提到 快照/累计/率 被 sum；或 trace 中 agg_type 为空 | `AGG_TYPE` 修正该列 summary | 根据根因关键词映射：快照→snapshot，累计→cumulative，率→avg |
| R9 | 拆分错误（规则） | 非口径类，fix_type = PROMPT_DECOMPOSE | `PROMPT_DECOMPOSE` 新建版本 | **不自动改写**，打开**提示词编辑器**（§5.3），基于当前激活版本新建草稿；系统在编辑器右侧给出"原问题 + 失败步骤 + 根因 + 相关规则条目定位"作为编辑参考 |
| R10 | 意图识别错误 | fix_type = KNOWLEDGE | `KNOWLEDGE` 追加业务知识条目 | 预填：根因说明文本，管理员精简 |
| R11 | 总结错误 | fix_type = PROMPT_SUMMARY | `PROMPT_SUMMARY` 新建版本 | 同 R9，打开总结提示词编辑器 |
| R12 | 总结错误 | 根因提到截断 | System B 配置 `TRUNCATE_*` | Phase 2，本期仅提示 |

> 规则产出的是**建议**，管理员可以逐条勾选、修改建议值、追加手动变更。所有建议值都在 UI 上以 diff 形式展示。

### 5.2 建议的置信度与标注

每条建议带 `confidence`：
- **高**：有明确定位字段支撑（如管理员填了应选表）→ 默认勾选
- **中**：基于 trace 推断（如 R7 embedding 相似）→ 默认勾选但标黄"请确认"
- **低**：需要人工编辑（R9/R11 提示词）→ 默认不勾选，提供编辑器入口

### 5.3 提示词编辑器

调优任务内嵌的提示词编辑器，用于 `PROMPT_DECOMPOSE` / `PROMPT_SUMMARY` 类变更。

**布局**（抽屉 / 全屏弹窗，三栏）：

| 左：参考信息 | 中：编辑区 | 右：diff |
|---|---|---|
| 原问题、失败步骤 JSON、根因说明 | 基于当前激活版本（如 `v1.0.5`）的全文，Monaco/CodeMirror，纯文本 | 与基线版本的逐行 diff（新增绿 / 删除红），实时更新 |
| **规则条目定位**：按根因关键词高亮相关规则（如含"累计"→ 跳到"规则十四之二 累计类指标处理"） | 支持查找替换、折叠规则段落（以 `规则N` / `【…】` 为锚点） | 统计：+N / −M 行，字数变化 |
| 历史版本列表（可切换基线） | 底部：版本号（自动 `v1.0.6`，可改）、描述（必填） | 「快速验证」：只跑原问题 1 题，秒级反馈 |

**约束**：
- 保存即新建 `prompt_version`（`is_active=0`）；版本号唯一校验
- 必填描述；diff 为空不允许保存
- 基础语法检查：占位符（如 `{{current_date}}`、`{{database_meta}}`）必须保留；JSON Schema 示例块括号配对
- 「快速验证」= 以 `prompt_overrides` 调 System B 跑原问题，不入验证报告，仅供编辑时试错
- 保存后该变更的 `after_value` = 新版本号，`diff_summary` = `+N/−M 行，基于 vX`

**System B 新增接口**：
- `POST /api/v1/prompts/version/create` `{group_id, base_version, content, version, description}` → 新建不激活
- `POST /api/v1/prompts/version/diff` `{group_id, from, to}` → 行级 diff（也可前端本地算）
- `POST /api/v1/prompts/lint` `{group_id, content}` → 占位符 / 括号检查

## 6. 草稿机制与验证

### 6.1 草稿隔离：各资产如何做到"改了但线上不生效"

这是设计的关键难点。不同资产采用不同策略：

| 资产 | 草稿策略 |
|---|---|
| 提示词 | 天然支持：新建版本但**不 switch**；验证时通过 `analyze` 请求参数 `prompt_overrides: {main: "v1.0.6-draft"}` 指定版本（System B 需新增该参数支持） |
| 表描述 / 别名 / agg_type / 枚举值 / 知识库 / 绑定表 | **元数据覆盖（meta override）**：验证时不改库，而是由 bi-manager 按任务的 `tuning_change` 列表在内存中生成"调优后的 database_meta"，通过 `analyze` 的 `database_meta` 参数直接传给 System B（该参数现已存在，chat-server 就是这么传的）。同时请求头带 `X-Tuning-Task: {task_id}`，System B 在该模式下**跳过 recall 缩圈**（因 recall 索引还是旧的），直接用传入的 meta |
| 召回配置 / 词典 | 验证时通过 recall 新增 `POST /api/recall/prod` 的 `config_overrides` 参数临时覆盖（recall 需新增）；若不支持则该类变更**跳过草稿、直接验证后发布**，并在 UI 标注"此类变更验证期间即生效" |

> **发布**时才真正写库 + 触发 `meta_sync` + `prompts/switch` + `rewrite/reload`。

### 6.2 验证集组装

验证集 = 以下四部分并集（去重），上限默认 30 题，可在任务页调整：

| 类型 | 来源 | 数量 | 作用 |
|---|---|---|---|
| ORIGIN | 本次诊断的原问题 | 1 | 必须修复 |
| SIMILAR | 同智能体、同主错误类型、涉及相同表/指标的历史问答（`chat_analysis_trace` 检索，优先有 👎 反馈的） | ≤ 10 | 验证是否顺带修好同类问题 |
| REGRESSION | `regression_case` 中同智能体、`tags` 命中本次变更资产（表名/指标 code）的用例 | ≤ 15 | **防退化**：确保没把对的改错 |
| MANUAL | 管理员在任务页临时添加 | 不限 | |

**期望值（expected）从哪来**：
- ORIGIN：诊断结论中的 `expected_table / expected_entities` + 管理员可选填"期望答案关键词"
- REGRESSION / 👍 沉淀：该问题当时的 trace（表、指标、维度）+ 答案 → 作为基线
- SIMILAR：若有诊断结论用诊断；否则只做"before/after 是否一致"的变化检测，不判对错，标 `verdict=CHANGED/UNCHANGED`

### 6.3 判定逻辑（Judge）

逐题对 after_result 做多维判定，任一必检维度失败即 FAIL：

| 维度 | 判定方式 | 必检 |
|---|---|---|
| 表 | `after.tables ⊇ expected.table` | 有期望时必检 |
| 指标 | `expected.metrics ⊆ after.metrics`（按 basic_id 或 code） | 同上 |
| 维度 | 同上 | 同上 |
| 执行状态 | after.status == success | 必检 |
| 答案关键词 | `expected.answer_keywords` 全部出现在 answer 中 | 有期望时 |
| 答案数值 | `expected.answer_value` 与 answer 中抽取的数值误差 ≤ 1% | 有期望时 |
| LLM 辅助判定 | 调 System B 已有 `batch_report.judge_errors` 做一致性判断（答案与数据是否自洽） | 可选，默认开 |

`verdict` 规则：

| before_pass | after_pass | verdict |
|---|---|---|
| ✗ | ✓ | **FIXED**（ORIGIN）/ IMPROVED |
| ✗ | ✗ | STILL_FAIL |
| ✓ | ✗ | **DEGRADED** ← 重点 |
| ✓ | ✓ | PASS |

报告 `conclusion`：
- `PASS`：origin FIXED 且 degraded = 0
- `PASS_WITH_WARN`：origin FIXED 但 degraded > 0 → 发布需二次确认并填写说明
- `FAIL`：origin STILL_FAIL（无论回归如何）

### 6.4 验证执行

- bi-manager 新增 `TuningVerifyService`，异步线程池执行，并发度默认 3（防止压垮 LLM 配额）
- 每题调 System B `POST /api/v1/analyze`，`request_id = "tuning-{task_id}-{case_id}"`（不含 `@`，System B 识别为测试模式，不走 chat-server 回调、不写会话），`skip_chat_clear=true`，带 `database_meta` 覆盖 + `prompt_overrides`
- **before 结果**优先复用历史 trace（ORIGIN / SIMILAR / REGRESSION 都有历史记录），没有的才现跑一遍 before，节省一半成本
- 进度写 `tuning_verify_report.case_done`，前端轮询或 SSE
- 超时：单题 120s，整体 30min；超时标 ERROR 不阻塞

### 6.5 发布与回退

**提交审批**（VERIFIED → PENDING_APPROVAL）：
1. 校验 conclusion ≠ FAIL；PASS_WITH_WARN 需填确认说明
2. 创建 permission 审批单（复用 `/approve` 模块，审批人 = 超级管理员角色），审批单内容：任务号、来源问题、变更摘要、验证结论、影响范围、确认说明
3. 通知超级管理员（站内 + 可选邮件）
4. 提交人可**撤回**（回到 VERIFIED）；验证报告在审批期间只读

**审批**（超级管理员）：
- 审批页可查看任务详情、验证报告（只读）
- **通过** → 系统自动执行发布
- **驳回** → 回到 VERIFIED，附驳回意见，提交人可修改建议重跑或回退

**发布**（审批通过后系统自动执行，PENDING_APPROVAL → PUBLISHED）：
1. 按 `tuning_change` 顺序逐条写入真实存储（事务按模块分段，跨模块不强一致，失败则记录到哪一条、支持"从失败处重试"）
3. 触发下游：recall `POST /api/metadata/sync`、System B `prompts/switch`、recall `rewrite/reload`
4. 关联的 `chat_error_diagnosis.fix_status = 已修复`，`chat_feedback.status = 已修复`
5. 原问题 + 本次验证通过的 SIMILAR 题自动沉淀为 `regression_case`（source=DIAGNOSIS）
6. 自动对原问题做一次**线上复验**（走完整链路含召回），结果记录到任务
7. 进入**观察期**（默认 7 天）：监控同智能体、同主错误类型的新增 👎；**24h 内 ≥ 2 条**触发告警（站内 + 任务页红色提示），由管理员决定是否回退。阈值在「设置」页可配

**回退**（VERIFIED / PENDING_APPROVAL / PUBLISHED → ROLLED_BACK）：
1. **不需要审批**（止损优先），但 PUBLISHED 回退后自动通知超级管理员
2. 读 `asset_snapshot`，逐条恢复 `snapshot_value`；提示词 switch 回 `snapshot_version`
3. 触发下游同步（同发布）
4. 若回退的是 PUBLISHED 任务：`fix_status` 退回"待修复"，并要求填写 `rollback_reason`
5. 回退后的任务可「复制为新任务」重新调整建议

**回退已发布的保护**：若该资产在本任务发布后又被**另一个已发布任务**改过，回退时提示冲突："字段 X 在 TN-005 中已被再次修改，回退将覆盖其变更"，需管理员选择 ① 仅回退本任务未被覆盖的字段 ② 强制全部回退。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 验证成本高（每题一次 LLM 拆解 + 可能多次总结） | before 复用历史 trace；验证集上限 30；并发 3；统计每任务 token 消耗展示在报告里 |
| 草稿 meta 与 recall 不一致导致验证结果与上线后不符 | 验证模式跳过 recall 用全量传入 meta，报告中标注"验证未经过召回缩圈"；发布后自动跑一次 ORIGIN 的线上复验（走完整链路）并在任务页展示 |
| 多人同时调同一资产 | 资产级占用锁（§4.2） |
| 回退覆盖后续变更 | 冲突检测 + PARTIAL/FORCE 模式（§6.5） |
| 建议质量差误导管理员 | 置信度分级；记录建议采纳率，低采纳率规则自动降级为"仅提示" |
| LLM 非确定性导致验证抖动 | 验证 temperature 固定 0；关键题可设"重复 N 次取多数"（Phase 2） |
