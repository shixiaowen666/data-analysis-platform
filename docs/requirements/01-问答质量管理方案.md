# 问答质量管理方案（用户反馈 + 管理端错误定位）

> 版本：v1.0　|　状态：已评审确认　|　原型：`docs/prototype/`（页面 ①–⑦）
>
> 后续：`03-自动调优设计.md`（定位后 → 调优 → 验证 → 发布/回退）

---

## 1. 需求

1. **管理端错误定位**：用户问数结果错误时，管理员可针对该问题进行错误定位。错误类型：
   选表错误 / 指标、维度提取错误 / 意图识别错误 / 拆分错误 / 总结错误
2. **用户反馈**：用户在问数过程中可提交反馈"结果错误"，错误原因可选：
   指标错误 / 维度错误 / 意图识别错误 / 拆分错误 / 选表错误 / 总结错误 / 结果错误，并可输入错误描述

## 2. 现状与差距

| 现状 | 差距 |
|---|---|
| `dcar_chat_model_qa` 有 `feedback`(1/-1) + `reason`，bi-manager 有 `POST /v1/chat/feedback` | 无错误类型枚举；**前端没有调用**，等于半成品 |
| 每步结果落 MinIO + `dcar_chat_model_qa` 一步一行，可通过 `/v1/chat/info`、`/v1/chat/step` 回看 | 能看"每步出了什么数据"，看不到"为什么这样选" |
| System B 写 `userlogs/{user}/{date}/问题N.log`（提示词 + 拆解 JSON + 每步输出）+ `user_operation_log` | **无 request_id / chat_id**，管理端无法从会话精确跳到日志 |
| System B analyze 响应含 `recall` 字段 | chat-server 只打日志，**未落库** |
| `/getdata/ai` 把 `expected_columns` 解析为指标/维度 ID、选表、生成 SQL | 解析结果只在日志，**未结构化保存** |
| 管理端 `aiLogManager` 只列日志文件 | 没有按会话组织的诊断视图 |

**结论**：错误定位的前提是"每一轮问答的全链路证据能按 `chat_id` 串起来"。方案第一件事是补**链路追踪（Trace）**，再做表单。

## 3. 总体设计

```
                 用户侧                                管理侧
   ┌──────────────────────────┐          ┌────────────────────────────────┐
   │ 问数页 👍 / 👎            │          │ 「问答质量管理」菜单            │
   │  👎 → 错误类型(多选7项)   │          │  ├ 用户反馈（待处理/已定位…）   │
   │       + 错误描述          │          │  ├ 问答诊断（全部会话可定位）   │
   └────────────┬─────────────┘          │  ├ 调优任务（见 03）            │
                │ POST feedback           │  └ 质量统计（Phase 2）          │
                ▼                         └───────────────┬────────────────┘
        ┌─────────────────┐      关联 chat_id      ┌──────────────────────┐
        │ chat_feedback   │◄──────────────────────►│ chat_error_diagnosis │
        │ (用户反馈)       │                        │ (管理员错误定位结论)  │
        └────────┬────────┘                        └──────────┬───────────┘
                 └──────────────► chat_analysis_trace ◄────────┘
                                  chat_step_trace
                                 (全链路证据，按 chat_id，系统自动记录)
```

- **chat_feedback**：用户主观分类 + 描述；一轮问答一个用户一条，可覆盖更新
- **chat_error_diagnosis**：管理员看完证据后的**权威结论**；一轮问答一条；可无反馈主动巡检
- **trace**：客观证据，系统自动记录，不可改

## 4. 错误类型字典（两侧统一编码）

| code | 名称 | 用户 | 管理 | 链路环节 | 定位依据 | 典型修复 |
|---|---|:-:|:-:|---|---|---|
| `INTENT` | 意图识别错误 | ✓ | ✓ | 拆解-理解问题 | steps description / 时间范围 vs 原问题 | 提示词、知识库 |
| `TABLE_SELECT` | 选表错误 | ✓ | ✓ | 召回 → 拆解选表 | 召回命中表 vs 拆解选表 vs 应选表 | 表描述、召回配置 |
| `METRIC_DIM` | 指标/维度提取错误 | — | ✓ | 取数映射 | 拆解列 → 映射 ID；未映射列 | 别名、描述、agg_type |
| `METRIC_DIM.METRIC` | └ 指标错误 | ✓ | ✓(细分) | 同上 | 同上 | 同上 |
| `METRIC_DIM.DIMENSION` | └ 维度错误 | ✓ | ✓(细分) | 同上 | 同上 | 同上 |
| `DECOMPOSE` | 拆分错误 | ✓ | ✓ | steps DAG / compute 参数 | steps JSON、execution_log 失败步骤 | 提示词、函数库 |
| `SUMMARY` | 总结错误 | ✓ | ✓ | summarize | 最终数据 vs answer | 总结提示词 |
| `RESULT` | 结果错误（说不清） | ✓ | — | 兜底 | 管理员定位后细化 | — |

## 5. 数据模型（`new_bi` 库）

### 5.1 `chat_analysis_trace` — 一轮问答一条（chat-server 收到 analyze 响应时写）
chat_session_id, chat_id(UK), ai_body_code, tenant_id, user_id, question, recall_enabled, recall_elapsed_ms, recall_tables(JSON), recall_metric_codes(JSON), recall_dim_codes(JSON), meta_table_count / meta_metric_count / meta_dim_count, decomposition_steps(JSON), execution_log(JSON), final_answer, status, system_b_log_path, total_elapsed_ms, llm_model, prompt_version, full_response_minio_path

### 5.2 `chat_step_trace` — 一个 query 步骤一条（chat-server `/getdata/ai` 写）
chat_id + step_id(UK), query_description, expected_table, expected_columns(JSON), resolved_table_id / name, resolved_indicator_ids / names(JSON), resolved_dimension_ids / names(JSON), **unmatched_columns(JSON)**, filters(JSON), time_range, group_expanded, sql, row_count, elapsed_ms, error_message

### 5.3 `chat_feedback`
chat_session_id, chat_id, ai_body_code, tenant_id, user_id, username, question, answer_snapshot, rating(1/-1), error_types(JSON), description(≤1000), status(0 待处理/1 已定位/2 已修复/3 已忽略), diagnosis_id, created_at, updated_at；UK(chat_id, user_id)

### 5.4 `chat_error_diagnosis`
chat_id(UK), chat_session_id, ai_body_code, tenant_id, primary_error_type, secondary_error_types(JSON), error_step_id, expected_table / actual_table, expected_entities / actual_entities(JSON), root_cause, fix_action_type, fix_action_detail, fix_status(0/1/2), diagnosed_by / at, verified_by / at

### 5.5 `chat_error_type_dict`
code, parent_code, name, scope(user/admin/both), pipeline_stage, sort, enabled

### 5.6 System B
`user_operation_log` + `request_id` 索引；新增 `POST /api/v1/logs/by-request`

> 兼容：`dcar_chat_model_qa.feedback/reason` 保留，提交反馈时同步镜像 rating。

## 6. 接口（bi-manager `/v1/chat/*`）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/v1/chat/error-types?scope=` | 字典 |
| POST | `/v1/chat/feedback` | 提交/更新反馈 `{chatSessionId, chatId, rating, errorTypes[], description}` |
| GET | `/v1/chat/feedback/mine?chatId=` | 回显 |
| GET | `/v1/chat/feedback/page` | 反馈分页 |
| PUT | `/v1/chat/feedback/{id}/status` | 忽略/关闭 |
| GET | `/v1/chat/trace/{chatId}` | 全链路：trace + step_trace + 各步结果 + 反馈 + 诊断 |
| GET | `/v1/chat/trace/{chatId}/system-b-log` | 代理 System B 日志全文 |
| GET | `/v1/chat/diagnosis/page` | 会话列表（含未反馈），筛"有反馈/执行失败/未定位" |
| POST | `/v1/chat/diagnosis/save` | 保存定位；关联反馈自动"已定位" |
| PUT | `/v1/chat/diagnosis/{chatId}/fix-status` | 修复/验证流转 |
| GET | `/v1/chat/quality/stats` | 统计（Phase 2） |

chat-server 内部：`biChat` 收到 `resolverResult` → 写 trace（完整响应落 MinIO）；`/getdata/ai` → 写 step_trace；均 try/catch 非致命。

## 7. 页面

### 7.1 用户侧（PC `newBI` + 移动端 `newBI-web`）
- 收到 `close` 后答案卡片底部出现 👍 👎
- 👎 弹窗：错误类型多选（7 chip）+ 错误描述（选填 ≤500，选"结果错误"时提示写清期望）
- 已反馈可修改；历史会话页同样可反馈
- 移动端 Vant ActionSheet

### 7.2 管理端「问答质量管理」
- **Tab 用户反馈**：筛选 → 列表（用户选的类型 vs 管理员定位结论）→ 去定位 / 忽略
- **Tab 问答诊断**：全部会话 + 快捷筛选 + 自动预判列 → 诊断页
- **诊断页**（三栏）：左 问答回放 · 中 链路追踪（①召回→②拆解→③取数映射→④执行→⑤总结，每环节右侧"判为 XX 错误"）· 右 定位表单（主因单选 + 细分、次因多选、出错步骤、应选表/应为实体、根因、修复方式 + 快捷跳转、加入回归集、**保存并生成调优建议**）
- **自动预判**：failed 步骤→拆分；unmatched_columns→指标维度；expected_table≠实际/UNKNOWN→选表；重试≥2→拆分；快照/累计被 sum→拆分；总结输入 0 行但有数值→总结
- **Tab 质量统计**（Phase 2）
