# 召回准确率 / 精准率提升方案

> 注：本文写于 v1.x 评审阶段。v2.0 已删除 `metadata_processor.py` / `index_builder.py`，其职责由 `app/entity/builder.py` / `sync_service.py` / `index_store.py` 承接；文中对旧文件的定位仅作历史记录。

> 评估日期：2026-09-29　基于 `database_meta.json`（272 指标 / 52 维度 / 70 表）与 `测试问题_llm.xlsx`（223 条）
> 状态标记：☐ 待处理　☑ 已处理　配套文档：`工程化问题清单.md`

## 一、数据分析结论（方案依据）

| 观察 | 数字 | 含义 |
|---|---|---|
| 期望指标名字面完整出现在问题里 | 148/300 = 49% | 一半 case 纯词法可命中，当前无词法通道 |
| 部分字面重叠（≥半数二元组） | 139/300 = 46% | 需子串 / n-gram 匹配 |
| 完全语义化（无字面线索） | 13/300 = 4% | 仅 4% 真正依赖 embedding 泛化 |
| 期望维度值为 "XX供电局" | 243/292 = 83% | 组织维度值是封闭集合，可规则抽取 |
| 问题含组织词 | 206/223 = 92% | 同上 |
| 期望表 description 为空 | 136/238 次 | 表级向量基本靠表名 + 指标名列表 |
| 期望指标名在 ≥2 张表同名 | 23/300 | 表消歧是刚需 |
| 多指标用例 / 多表用例 | 51 / 14 | 意图拆分需覆盖 1/4 用例 |
| 时间表达 | ISO 日期 63、X月 60、年月 45、同环比 37 | 时间剥离质量影响 1/3 以上用例 |

**结论**：本场景本质是「封闭词表上的实体链接 + 表消歧」，而非开放域语义检索。方向：词法通道补进来，结构化实体走规则，embedding 退到兜底和泛化位。

## 二、改动清单

### 层级 0：数据层（决定上限）

#### 0-1 补全描述 + 生成典型问法 ☐
- 涉及：`app/services/meta_enricher.py`、`app/services/enrich_prompts.py`、`app/core/text_builder.py`、`app/services/metadata_processor.py`
- 现状：97% 指标无描述；`text_builder` 已预留 `typical_questions` 字段但 `metadata_processor._process_metrics/_process_dimensions/_process_tables` 从未填充。
- 改动：
  1. `meta_enricher` 新增 target `typical_questions`：为每个指标/维度/表用 LLM 生成 3~5 条口语问法，以测试集问题为风格样本。
  2. `database_meta.json` 指标/维度/表条目增加 `typical_questions: []` 字段；`gen_database_meta.py` 生成时保留该字段（不从库覆盖）。
  3. `metadata_processor` 把 `typical_questions` 传入 `text_builder`，进入 embedding_text。
- 预期：拉近 query 分布与文档分布，embedding 场景下最便宜有效。

#### 0-2 按表建实体，解决同 code 多义 ☐
- 涉及：`metadata_processor._infer_mappings/_process_metrics/_write_relations`、`core/schema.py`（meta_metric 增 `table_id` 或新增 `meta_table_column`）、`core/index_builder.py`、`services/slim_exporter._build_metrics`、`services/relation_registry.py`
- 现状：以 `metric_code` 去重，`ll_rate` 7 张表只有一个实体"分区线损率"，embedding 文本无"分压/分台区/分线"字样；测试集 11 条期望指标被迫留空（#46/49/54/60/84/85/135/138/188/191/215）。
- 改动：实体主键改为 `(table_id, column_name)`，`display_name`/`description` 取该表的列描述；`available_metrics` 中的全局条目仅作 code→单位/别名的字典。slim 导出时按表输出对应名称。
- 预期：解决 38 个多义列名；同时修复上述 11 条用例。

#### 0-3 组织维度归一化 + 维度值/别名分离 + 层级规则代码化 ☐
- 涉及：`metadata_processor._process_dimensions/_process_dim_values`、`data/domain_knowledge.json`（新增 `org_dimension_map`、`dim_value_aliases`）、`services/slim_exporter.py`
- 现状：9 个组织 code（`org_name/supply_org_name/org_short_name/dis_org_short_name/city_org_short_name/supply_org_no/org_no/region_code/regioncode`）表达同一概念；3 个共享 34 个 possible_values，"深圳供电局"三份向量、投票三倍放权；`org_name` 的值里混有"福田局/福田供电局"。business_context 第一条"市局用 city_org / 区局用 dis_org / 仅 gdj 用 org_name"规则仅是文本，代码未消费。
- 改动：
  1. 建"逻辑维度"层：9 个 code → 1 个逻辑维度"组织机构"，向量只建一份；`rel_table_dimension` 仍按物理 code 挂表。
  2. 维度值规范化：34 值 → 12 规范值（深圳 + 11 区局）+ 分局，`XX局/XX/XX区` 进 synonyms 而非 possible_values。
  3. 新增 `org_level_rules` 配置：`{level: 市局|区局|分局 → 候选列优先级 [city_org_short_name, dis_org_short_name, branch_org_name, org_name]}`；slim 导出时按选中表实际拥有的列挑正确组织维度。
- 预期：消除组织维度重复候选；表消歧时组织列选择正确。

#### 0-4 清理旧领域规则（同问题清单 #2/#3） ☐
- 涉及：`data/domain_knowledge.json`、`metadata_processor.py:52-115`
- 改动：重写 `topic_definitions`（按当前 8 大业务域：供电量/用电量/光伏/线损/抄表率/计量档案/电能质量/电力交易）；删除或按当前领域重写 `METRIC_SYNONYMS_PATTERN`/`UNIT_INFERENCE_RULES`；派生指标规则改为从 business_context 自动抽取。

### 层级 1：检索层（混合检索）

#### 1-4 新增 BM25 词法通道 + RRF 融合 ☐ ★性价比最高
- 涉及：新增 `app/core/lexical_index.py`；`core/index_builder.py`（构建时同时建 BM25）；`services/recall_service.py`（新增 Path L 或在 A/C 内并行查词法）；`recall_config` 新增 `path_lexical` 配置；`requirements.txt` 加 `rank_bm25` + `jieba`（或用 SQLite FTS5 字 n-gram）
- 现状：单一 dense 通道，对"分区线损率 vs 分压线损率"一字之差区分弱。
- 改动：
  1. 对每个实体的 `embedding_text`（或 display_name + synonyms + typical_questions）建 BM25，分词用 jieba + 字二元组双索引。
  2. 每路召回同时取 dense top-k 与 BM25 top-k，用 RRF（k=60）融合，融合分写入 `RecallResult.score_lexical`/`score_fused`。
  3. 配置项：`LEXICAL_ENABLED`、`RRF_K`、`LEXICAL_WEIGHT`。
- 预期：指标命中率提升最明显；95% 用例有字面线索。

#### 1-5 确定性实体抽取通道 + query 结构化 ☐
- 涉及：新增 `app/services/query_parser.py`（合并现有 `recall_service._strip_time` 与 `intent_splitter`）；`services/recall_service.recall`；`services/slim_pipeline.py`
- 现状：维度值 83% 供电局、12% 用户类型、3% kV 等级，全是封闭枚举，却走向量；时间剥离正则切碎查询（问题清单 #8）。
- 改动：
  1. 用 Aho-Corasick / 最长匹配从 query 抽出组织、用户类型、电压等级、产业、业扩类型等封闭枚举值，置信度 1.0 直接进候选（`source="extract"`）。
  2. 规则：`XX局→XX供电局`；`深圳/全市/整个深圳→深圳供电局`；`各区局/11个区局/各供电局→选维度不选值`；无组织词→缺省深圳供电局（business_context 第三条）。
  3. 抽取后从 query 挖掉实体词与时间词，得到 `residual_text` 用于指标检索；输出结构 `{time_terms, orgs, dim_values, residual, sub_intents}`。
  4. 时间剥离改为可配置模式列表 + 单测，修复 `2026年7月1日与6月15日相比 → 与 15日相比`、`上个月` 未匹配等 case。
- 预期：维度值命中接近 100%；指标向量更干净。

#### 1-6 表选择改为「实体反推为主、表向量为辅」 ☐
- 涉及：`services/recall_service._path_a_recall`、`services/relation_registry.table_votes`、`services/table_gate.py`、`services/slim_pipeline.py`、`metadata_processor._process_tables`（表 embedding_text）
- 现状：Path A 先选 top-3 表再表内找实体，表向量因 136/238 期望表无 description 而弱，选错表整路白费。
- 改动：
  1. 全局实体检索（dense + BM25）→ 按 `legal_tables` 投票 → 表得分 = 实体票 + 表向量分 + 表中文名/列中文名 BM25 分。
  2. Path A 改为：先做全局实体检索，再用投票 top-N 表做表内精排；`table_gate` 逻辑前移为主排序器。
  3. 表 embedding_text 改为「表中文名 + 列中文名 bag + typical_questions」。
  4. 月表/日表消歧：`description` 含"查询日期为月度的则查本表"的 8 张月表，加规则——query 时间粒度为月且无具体日期时提升月表得分。
- 预期：表命中率与表消歧提升。

#### 1-7 意图拆分升级 ☐
- 涉及：`services/intent_splitter.py`、`services/query_parser.py`
- 现状：依赖词典锚点，241/272 指标无别名导致锚点少。
- 改动：
  1. 补别名后锚点自然增加（依赖 0-1）。
  2. 共享前缀省略结构做前缀继承："光伏上网电量、用电电量、发电电量" → "光伏用电电量"、"光伏发电电量"。
  3. 锚点 <2 但含顿号/"和"/"分别"时，slim 链路可选 LLM 轻量拆分（结果按 query 缓存）。
- 预期：覆盖 51 条多指标用例。

#### 1-8 Embedding 本地化 + 微调（中期） ☐
- 涉及：`core/embedding.py`（支持本地 TEI/vLLM 端点）、新增 `scripts/build_finetune_pairs.py`、`scripts/finetune_embedding.py`
- 改动：
  1. 部署 `bge-m3` 或 `Qwen3-Embedding-0.6B`，`EMBEDDING_API_BASE_URL` 指向本地；编码延迟 800ms → 数十 ms，多子查询成本可接受。
  2. 用 223 条标注 + judge 选中日志构造 (query, 正例实体文本, 难负例=同表/同名近邻) 三元组，sentence-transformers 对比学习微调。
- 预期：窄域微调通常提升 5~10 个点。

### 层级 2：排序层（提精准率）

#### 2-9 Reranker 换成真打分 ☐
- 涉及：`core/reranker.py`、`services/recall_service._candidate_text/_rerank`、`.env` RERANK_*
- 现状：LM Studio `/v1/completions` 输出 yes/no，得分是 0/1 二值，30 候选可能 20 个 yes，排序信息几乎为零。
- 改动：
  1. 改为读 `yes` token 的 logprob（vLLM/TEI 部署 Qwen3-Reranker）或直接用 `bge-reranker-v2-m3` 的 `/rerank` 端点返回连续分。
  2. 重排文档文本加入表名 + 列描述，让 cross-encoder 能做表消歧。
  3. `RERANK_TOP_N` 按类型分别设置。

#### 2-10 候选集收缩策略 ☐
- 涉及：`services/slim_exporter._export_candidates/_export_selected`、`services/recall_service._merge_and_deduplicate`、`recall_config`
- 现状：slim 导出 = 选中实体 ∪ 允许表上的所有候选实体，精准率天然低；Path C 全局兜底始终开启。
- 改动：
  1. 相对阈值：分数 < top1 × `RELATIVE_CUTOFF`（默认 0.7）的截掉。
  2. 每类型 top-k 上限进 config。
  3. Path C 仅在 Path A 结果少于 N 时启用（`PATH_C_FALLBACK_MIN`）。
  4. 可选 LTR：LightGBM，特征 = dense 分、BM25 分、命中路径数、字面重叠率、表票数、是否被实体抽取命中；223 条标注可训。

#### 2-11 LLM 精判增强 ☐
- 涉及：`data/prompts/judgment.md`、`services/llm_judge.py`、`app/config.py`（judge 模型可独立配置）
- 现状：prompt 规则仍是旧领域（"地调/统调/中调"、"跳闸次数"）；候选是 100 行扁平列表。
- 改动：
  1. 规则换为当前领域：组织层级 → 列映射、月表 vs 日表、`gdj` 表特例、用户类型别名（低压=公变客户、专变=公线专变+专线专变）。
  2. 输入按表分组：每张表下列出其候选指标/维度，LLM 做"选表 → 选列"两步。
  3. 从测试集抽 5~8 条典型 case 做 few-shot。
  4. `/prod` 接口 judge 用小模型（qwen-plus/turbo）压延迟，`JUDGE_MODEL` 独立于 `LLM_MODEL`。

### 层级 3：评估与闭环

#### 3-12 修评估口径 ☐
- 涉及：`services/batch_test_service.judge_case/_build_stats/export_xlsx`、`static/index.html` 批测页
- 现状：只有召回视角命中率，且 `_contains_any` 双向子串宽松匹配（问题清单 #20）；无精准率指标。
- 改动：
  1. 匹配规则改为「期望 ⊆ 实际」单向 + 精确/别名匹配，去掉反向包含。
  2. 新增每类型 P / R / F1、P@5 / P@10、MRR、平均导出规模（指标/维度/表数）。
  3. 失败原因自动归类：表选错 / 指标漏 / 同名消歧错 / 维度值漏 / 意图漏，报告按原因分组。
  4. 汇总 Sheet 增加精准率列；明细增加"多余项"列。

#### 3-13 难例挖掘 + 回归集 ☐
- 涉及：`services/batch_test_service.py`、新增 `data/hard_cases.xlsx`、新增 `scripts/regression.py`
- 改动：
  1. 每次批测未命中 case 自动追加到 `hard_cases.xlsx`（去重）。
  2. `regression.py`：改动后先跑回归集，命中率下降超阈值报警。
  3. `/prod` 请求 + judge 输出落库（新增 `recall_log` 表），定期抽样人工标注扩充测试集；当前 44/70 张表有用例，26 张零覆盖需补。

#### 3-14 A/B 基础设施 ☐
- 涉及：`core/config_manager.py`、`recall_config` 表（新增 `strategy_flags` 或独立 `strategy_config` 表）、批测接口 `BatchRunRequest` 增 `strategy` 参数
- 改动：策略开关（BM25 / 实体抽取 / reranker / 相对阈值 / 表反推）可按请求覆盖；批测支持一次提交多组策略并排对比。
