# LOGIC-ARCHITECTURE.md

## 1. 文档定位

本文档用于约束 `semantic-server` 的逻辑架构。

与 `AGENTS.md` 的分工如下：

- `AGENTS.md` 负责约束技术架构、技术栈、目录结构、编码规范
- `LOGIC-ARCHITECTURE.md` 负责约束业务主流程、领域边界、核心决策规则、SQL 生成语义

后续即使实现方式发生变化，只要本文件未变，核心业务行为就不应随意变化。

---

## 2. 核心目标

`semantic-server` 的核心职责不是简单查表，而是将“业务查询意图”转换为“可执行的数据查询逻辑”。

其标准闭环如下：

1. 接收查询请求
2. 解析维度、指标、过滤条件、分页等业务语义
3. 选择满足条件的底层数据源
4. 将语义请求转换为 SQL
5. 执行 SQL
6. 返回统一结果

本服务的核心价值在于：

- 对上游暴露统一语义查询入口
- 对下游屏蔽底层表结构和模型关联细节
- 通过规则化选择数据源和生成 SQL，保证查询逻辑一致性

---

## 3. 核心领域对象

### 3.1 QueryRequest

查询请求至少包含以下逻辑元素：

- `dimensionIds`：用户要查询的维度列表
- `indicatorIds`：用户要查询的指标列表
- `preferredTableIds`：用户指定优先查询的单表范围
- `preferredModelIds`：用户指定优先查询的模型范围
- `filters`：维度过滤和指标过滤
- `paging`：分页参数
- `timeRange`：时间范围参数

### 3.2 DataSourceInfo

`DataSourceInfo` 是数据源选择阶段和 SQL 生成阶段之间的标准中间对象。

它描述的不是“数据库连接”，而是“一次查询最终要落到哪个逻辑数据源上”。

必须包含的信息：

- 数据源类型：`1-单表`，`2-model`
- `tableId` 或 `modelId`
- `dbName`
- `tableName`
- `dimensionFields`
- `indicatorFields`

### 3.3 FieldMappingInfo

字段映射对象用于表达“业务字段”和“物理字段”的映射关系。

至少应承载：

- 业务字段 ID
- 业务字段 key
- 物理字段名 `srcField`
- 物理字段类型
- ETL 类型与说明

### 3.4 Table

单表是可直接查询的最小数据源。

单表具备以下逻辑特点：

- 可独立完成 SQL 查询
- 不需要额外 join 关系即可执行
- 维度和指标都必须能在该表映射到物理字段

### 3.5 Model

Model 是由一个事实表和一个或多个维度表组成的逻辑数据源。

Model 的逻辑约束：

- 每个 model 必须有且仅有一个事实表
- 每个 model 可以有一个或多个维度表
- 表间关系由 `olap_fact_dim_mapping_pro` 定义
- SQL 生成时必须根据映射关系构建 join

---

## 4. 主流程总览

完整主流程固定为以下顺序：

1. 接收请求
2. 校验请求参数
3. 选择数据源
4. 生成 SQL
5. 执行 SQL
6. 合并结果
7. 封装统一响应

逻辑上不允许跳过“数据源选择”直接生成 SQL。

也不允许跳过“字段映射”直接使用外部传入字段名拼接底层表 SQL。

---

## 5. 数据源选择逻辑

数据源选择必须分为两个阶段：

1. 维度阶段
2. 指标阶段

维度阶段决定“哪些数据源有资格参与查询”。

指标阶段决定“在合格候选中最终选择哪些数据源”。

### 5.1 维度阶段

维度阶段的目标是：

从单表和 model 中筛选出“能够覆盖全部目标维度”的候选数据源。

处理规则：

1. 根据 `dimensionIds` 查询字段映射关系
2. 单表场景下，按 `tableId` 聚合字段映射
3. 如果某个表覆盖全部 `dimensionIds`，则该表成为候选
4. model 场景下，根据 `olap_fact_dim_mapping_pro` 收集 model 关联表
5. 如果某个 model 覆盖全部 `dimensionIds`，则该 model 成为候选
6. 如果传入 `preferredTableIds` 或 `preferredModelIds`，维度阶段必须优先在该范围内筛选

维度阶段失败时，必须立即终止流程并返回明确错误，不进入指标阶段。

### 5.2 指标阶段

指标阶段的目标是：

在维度阶段候选中，选出能够覆盖全部目标指标的最优数据源集合。

处理规则：

1. 先为每个候选数据源补充可覆盖的指标字段
2. 构建总指标池
3. 如果目标指标不在指标池内，直接失败
4. 使用贪心算法，每次选择“覆盖剩余指标最多”的候选数据源
5. 循环直到全部指标被覆盖

当前阶段允许多个数据源共同覆盖全部指标。

即：

- 不要求一个数据源独占全部指标
- 允许两个或多个表 / model 共同完成一次查询请求

### 5.3 预选范围规则

当用户传入 `preferredTableIds` 或 `preferredModelIds` 时，逻辑规则如下：

1. 预选范围是硬约束，不是软提示
2. 若预选范围内找不到满足维度的候选，直接报错
3. 若预选范围内维度满足但指标无法覆盖，直接报错

不允许在预选失败后自动回退到全量表范围。

## 6. 单表查询逻辑

### 6.1 单表定义

单表是指：

不依赖任何 join，就可以直接对底层物理表发起查询的数据源。

### 6.2 单表 SQL 标准结构

单表 SQL 的标准结构如下：

```sql
SELECT 维度字段, 聚合指标字段
FROM db_name.table_name
WHERE 维度过滤条件
GROUP BY 维度字段
HAVING 指标过滤条件
```

### 6.3 单表 SQL 规则

1. `SELECT` 中维度字段直接取物理字段
2. `SELECT` 中指标字段默认按聚合函数输出，当前阶段默认 `sum`
3. `WHERE` 只处理维度过滤
4. `GROUP BY` 只对维度字段分组
5. `HAVING` 只处理指标过滤

### 6.4 单表场景的字段归属

单表场景下：

- 所有维度字段必须来自当前表
- 所有指标字段必须来自当前表

如果某个维度或指标无法映射到该表，则该表不能成为合法数据源。

---

## 7. Model 查询逻辑

### 7.1 Model 定义

Model 是以事实表为核心，挂接一个或多个维度表的逻辑查询单元。

### 7.2 Model 结构约束

当前阶段强约束如下：

1. 每个 model 必须有一个事实表 `fact_tb`
2. 每个 model 可以有多个维度表 `dim_tb`
3. 表关系必须来自 `olap_fact_dim_mapping_pro`
4. join 类型必须由 `join_type` 决定

`join_type` 解释固定如下：

- `0`：`INNER JOIN`
- `1`：`LEFT JOIN`
- `2`：`RIGHT JOIN`

### 7.3 Model SQL 标准结构

```sql
SELECT 维度字段, 聚合指标字段
FROM fact_tb t1
JOIN dim_tb t2 ON t1.fact_field_key = t2.dim_field_key
JOIN dim_tb t3 ON t1.fact_field_key = t3.dim_field_key
WHERE 维度过滤条件
GROUP BY 维度字段
HAVING 指标过滤条件
```

### 7.4 Model SQL 规则

1. `FROM` 必须先落到 fact 表
2. 所有 dim 表必须按映射关系 join 到 fact 表或已存在 join 链
3. `SELECT` 中维度字段来自其真实映射所在表
4. `SELECT` 中指标字段默认来自 fact 表并按聚合输出
5. `WHERE` 处理维度过滤
6. `GROUP BY` 处理维度字段
7. `HAVING` 处理指标过滤

### 7.5 当前阶段与最终目标

当前阶段允许先实现为：

- join 关系可稳定生成
- 默认指标来源于 fact 表

但长期目标必须是：

- 维度字段根据字段映射精确判断来自 fact 还是 dim
- SQL builder 不允许默认把全部维度字段写死在 fact 表别名上

---

## 8. Filter 语义规范

`filters` 是查询语义中最关键的输入之一。

### 8.1 Filter 结构

每个 filter 至少包含：

- `type`
- `field`
- `operator`
- `values`

### 8.2 Filter 类型语义

#### `type = dimension`

表示维度过滤，必须下沉到 `WHERE`。

#### `type = indicator`

表示指标过滤，必须下沉到 `HAVING`。

### 8.3 Operator 规则

当前阶段建议固定如下：

- 维度过滤允许：`in`、`notin`
- 指标过滤允许：`>`、`>=`、`<`、`<=`、`=`、`!=`

不允许维度过滤直接使用数值比较操作符。

不允许指标过滤直接使用多值 `in` 语义替代数值比较。

### 8.4 Field 语义规则

`field` 在逻辑上表示“业务可识别字段”，不是任意外部拼接的物理列名。

因此后续正式实现中必须满足：

1. `field` 必须能映射到合法字段
2. `field` 必须属于当前选中数据源
3. 不允许用户传入任意底层列名直接进入 SQL 拼接

---

## 9. SQL 生成边界

SQL 生成阶段只负责一件事：

把已经确定好的 `DataSourceInfo` 和过滤条件翻译成 SQL。

SQL 生成阶段不负责：

- 再次决定选哪个表
- 修改数据源选择结果
- 解释用户真正想查什么
- 推断不存在于元数据中的字段

### 9.1 SQL Builder 的输入边界

输入必须是已经完成选择的数据源和字段映射。

### 9.2 SQL Builder 的输出边界

输出必须是可执行 SQL，或 SQL 中间结构。

当前阶段采用“每个数据源生成一条 SQL”的策略。

即：

- 一个 `DataSourceInfo` 对应一条 SQL
- 多个数据源对应多条 SQL

---

## 10. 执行与结果合并逻辑

当前阶段执行策略如下：

1. 遍历 SQL 列表
2. 每条 SQL 单独执行
3. 将结果集读入内存
4. 将多个结果集在服务层合并
5. 返回统一结构

### 10.1 当前策略的适用前提

该策略适用于：

- 当前功能验证阶段
- 多个数据源分别出结果后可直接合并
- 不追求复杂分布式优化

### 10.2 后续可演进方向

后续如有需要，可以演进为：

- SQL 层合并
- 中间结果归并层
- 多数据源统一分页

但当前阶段不强制要求。

---

## 11. 错误场景与处理规则

以下错误场景必须显式处理：

### 11.1 维度无候选

当没有任何表或 model 能覆盖全部维度时，必须报错。

### 11.2 指标无法覆盖

当维度候选存在，但所有候选合起来仍无法覆盖全部目标指标时，必须报错。

### 11.3 预选范围无结果

当用户传入预选范围，而预选范围无法满足维度或指标时，必须报错，不自动回退。

### 11.4 Model 关系不完整

当 model 缺少 fact 表、join 字段、dim 表或 join_type 非法时，必须视为 model 不可用。

### 11.5 非法过滤条件

当 filter 的 `type`、`field`、`operator`、`values` 不合法时，必须拒绝执行。

---

## 12. 当前阶段强约束

当前阶段必须固定以下逻辑约束：

1. 数据源类型只允许两种：单表、model
2. 数据源选择必须先维度后指标
3. model 必须以 fact 表为核心
4. filter 中维度条件进入 `WHERE`
5. filter 中指标条件进入 `HAVING`
6. 单表和 model 的字段都必须走字段映射
7. 不允许外部输入直接拼接 SQL 结构片段
8. 当前阶段默认指标聚合函数为 `sum`
9. 当前阶段允许一个请求生成多条 SQL
10. 当前阶段允许多个数据源共同覆盖目标指标

---

## 13. 当前阶段暂不承诺的能力

以下能力不应默认认为已经支持：

1. 指标多聚合函数自动识别
2. SQL 全参数化安全重写
3. 多数据源统一大 SQL 优化
4. model 多层复杂 join 排序优化
5. 动态聚合函数推导
6. 动态窗口函数
7. 自动分库分表路由
8. 智能成本优化选表

后续如需支持，必须先补充本文件的逻辑约束，再落地实现。

---

## 14. 一句话总结

`semantic-server` 的逻辑本质是：先根据维度和指标选择最合适的数据源，再基于字段映射和过滤语义生成 SQL，最后执行并返回统一结果。其中，维度决定候选资格，指标决定最终选择，单表与 model 只是在 `FROM / JOIN` 层面表现不同。
